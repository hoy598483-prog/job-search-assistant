# 产品经理知识库（整合版）

> 用于 Coze 知识库导入，面向产品经理和 AI 产品经理的通用工作方法。它提供方法与模板，不替代真实用户研究、业务数据、岗位原文、法律意见或实时市场事实。

## 使用原则

1. 先确认用户、场景、目标和限制，再选方法。
2. 将事实、假设、意见和待验证项分开。
3. AI 输出需要来源、限制和失败路径；不能因语言流畅就视为正确。
4. 先做最小验证，再扩大范围。

# 产品基础：从问题到价值

## 产品经理的核心职责

产品经理的工作不是收集功能，也不是替用户说“想要什么”。核心是识别有价值的问题，在资源、时间和风险约束下定义一个可验证的解决方案，并推动它被做出来、被使用和被改进。

## 问题定义

一个合格的问题陈述包含：

- **用户**：谁在什么角色、什么条件下遇到问题。
- **场景**：问题发生在什么时候、之前做什么、之后要完成什么。
- **痛点**：当前方案造成的时间、错误、成本、风险或机会损失。
- **结果**：用户希望获得的可观察变化。
- **边界**：首版明确不解决什么。

示例：

> 正在投递多个 AI 产品岗位的求职者，需要比较多条 JD 中共同出现的能力要求。当前只能手工整理，容易把加分项误当成硬门槛。首版帮助其保留原文依据、识别共同能力并生成当天任务；不做自动投递或录用概率预测。

## 用户价值与业务价值

用户价值回答“用户为什么愿意使用”；业务价值回答“组织为什么值得投入”。二者不能互相替代。

| 层次 | 典型问题 |
| --- | --- |
| 用户价值 | 节省什么时间？减少什么错误？提高什么确定性？ |
| 业务价值 | 提升留存、转化、效率、收入或降低风险？ |
| 实现价值 | 在现有数据、技术和人力下是否可交付、可维护？ |

## 需求、方案与功能的区别

- **需求**：用户在特定场景下需要达成的结果。
- **方案**：解决需求的一种方式。
- **功能**：方案中可操作的具体能力。

例如，“我想知道该补什么能力”是需求；“按多条 JD 生成能力地图”是方案；“上传 JD”“显示原文引用”是功能。

## 最小可行产品（MVP）

MVP 不是功能最少，而是用最小成本验证最关键假设的版本。定义 MVP 时写下：

1. 要验证的假设；
2. 最小用户流程；
3. 成功或失败的观测信号；
4. 不做的功能；
5. 验证后可能的下一步。

## 常见误区

- 先选技术再找问题；
- 将“用户说想要”直接等同于需求；
- 功能很多但没有成功标准；
- 把一次成功演示当成产品验证；
- 不写不做什么，导致范围持续扩张。

# 用户研究：从描述到可验证洞察

## 研究目标

用户研究用来减少不确定性，不是为了证明既定方案正确。研究前先写清楚要回答的决策问题，例如：

- 用户是否真的频繁遇到该问题？
- 当前如何解决，成本是什么？
- 哪个步骤最值得优先改善？
- 用户是否理解并愿意采用新方案？

## 常见方法

| 方法 | 适合回答 | 局限 |
| --- | --- | --- |
| 访谈 | 动机、场景、决策过程、语言表达 | 样本小，用户可能事后合理化 |
| 可用性测试 | 是否能完成任务、哪里困惑 | 不能直接证明市场规模 |
| 行为数据 | 真实使用频率、漏斗、留存 | 不一定解释“为什么” |
| 问卷 | 已知选项的分布和筛选 | 不适合发现深层动机 |
| 社区帖子 | 痛点线索、术语、项目灵感 | 代表性未知，不能直接当市场事实 |

## 从观察到洞察

一条洞察应包含证据和解释，不只是结论。

```text
观察：3 位求职者在比较多条 JD 时自行复制到表格。
解释：他们需要看到重复能力和来源，而不只是一个匹配分数。
假设：若系统显示每项能力的 JD 原文，用户更愿意采用计划。
验证：让用户完成一次比较任务，观察是否能解释每项结论来自哪里。
```

## 访谈提问原则

- 问过去发生的真实行为，不先问“你会不会使用这个功能”。
- 请用户描述最近一次、具体场景、实际步骤和卡点。
- 少用诱导性问题，例如“你是否觉得 AI 很有帮助”。
- 将用户原话、研究者推断和待验证假设分开记录。

## 研究记录格式

| 字段 | 内容 |
| --- | --- |
| 资料来源 | 访谈、可用性测试、数据、帖子或用户提供材料 |
| 原始证据 | 原话、截图、行为记录或数据链接 |
| 观察 | 可直接从证据看到的现象 |
| 推断 | 对原因的解释 |
| 信心 | 高、中、低，以及原因 |
| 下一步 | 要验证、放弃或实施什么 |

# PRD、优先级与路线图

## 精简 PRD 结构

一份能支持研发和评审的 PRD，通常包含：

1. 背景和问题；
2. 目标用户与使用场景；
3. 成功标准；
4. 用户流程；
5. 功能需求和异常路径；
6. 数据、权限、隐私和技术约束；
7. 不做什么；
8. 验收标准与上线后观察指标。

## 好需求的写法

用“当……时，用户可以……，从而……”描述行为与结果；再补充验收条件。

```text
当用户提交多条招聘简介时，系统可以分别展示每项能力的原文来源和条件关系，
从而避免将加分项误解为硬门槛。

验收：含“优先”的原文不会被标为 required；每条结论可定位到输入文本。
```

## 优先级

优先级不需要复杂公式，但必须写出判断理由。一个实用的顺序是：

1. 是否直接解决核心用户问题；
2. 是否是后续功能的前置依赖；
3. 是否降低明显风险或错误；
4. 验证成本是否低；
5. 是否有足够证据支持现在做。

可使用 RICE、影响/成本矩阵或简单的“必须、应该、可以、暂不做”分类。框架用于辅助讨论，不替代判断。

## 路线图

路线图按用户结果和验证阶段组织，而不是按团队或技术名词罗列。

```text
阶段一：用户能提交材料并看到可追溯分析。
阶段二：用户能根据分析选择项目并完成第一个任务。
阶段三：用户提交成果后，计划能有依据地调整。
```

## 需求变更

需求变更时记录：变更原因、证据、影响范围、放弃内容和验证方式。保留计划版本，避免后来无法解释为何改变方向。

# 指标、实验与复盘

## 指标层次

| 层次 | 说明 | 示例 |
| --- | --- | --- |
| 北极星结果 | 用户真正获得的结果 | 用户完成一份可执行的求职准备计划 |
| 行为过程 | 结果前的关键动作 | 提交 JD、查看引用、选择项目、提交成果 |
| 质量与风险 | 系统是否可靠、安全、可理解 | 引用正确率、编造率、失败率、耗时 |
| 商业指标 | 组织层面的收益 | 留存、付费、成本、转化 |

不要只优化容易增长的点击或对话轮数；它们可能和用户成功无关。

## 假设与实验

```text
假设：显示 JD 原文引用会提升用户对能力差距报告的信任。
改动：在每个结论下显示来源片段。
对照：没有来源的摘要。
指标：用户能否正确解释结论来源；是否主动纠正错误；是否采纳计划。
风险：来源过多会降低可读性。
```

实验前明确：样本、时间、成功门槛、可能的副作用和停止条件。

## 评测（尤其适用于 AI 产品）

评测集应包含正常案例、边界案例、失败案例和对抗案例。对每个案例写：输入、期望行为、不可接受行为、判定方法。

例如：

| 输入 | 期望行为 | 不可接受行为 |
| --- | --- | --- |
| “有海外经验者优先” | 标记为加分项 | 写成必须有海外经验 |
| “至少一项 RAG/知识图谱” | 保留择一关系 | 要求同时掌握全部技术 |
| 非招聘文本 | 说明无可分析要求 | 编造岗位能力结论 |

## 复盘

复盘关注决策质量，不只看结果。记录：目标、实际结果、证据、意外情况、根因、保留/改变/停止的决策，以及下一次验证方式。

# AI 产品：模型能力、边界与体验

## LLM 的基本工作方式

大语言模型根据输入上下文生成输出。它擅长理解和生成语言、提取结构、归纳、改写和在有限工具范围内规划步骤；它不天然保证事实正确、计算精确、来源可追溯或长期记忆可靠。

产品设计需要区分：

- **模型判断**：语言理解、分类、摘要、生成候选方案。
- **规则判断**：权限、格式、预算、状态转换、确定性约束。
- **外部事实**：数据库、检索结果、用户上传材料、工具返回值。

## RAG

RAG 指先从资料中检索相关片段，再将其提供给模型回答。它适合资料多、需要来源或信息常更新的情况。

关键问题：资料是否可信、如何切分、召回是否完整、回答是否引用、找不到资料时如何提示。资料较少时，直接处理原文可能比搭建 RAG 更简单。

## Agent 与工作流

- **工作流**：步骤和分支主要由产品设计者预先定义，适合稳定、可验证的任务。
- **Agent**：模型在工具和规则边界内决定下一步，适合步骤数量或路径难以预测的任务。

先用工作流跑通，只有固定路径无法满足用户需求时再增加 Agent 决策。无论哪种方式，都需要状态、停止条件、错误处理和人工确认点。

## AI 输出可信度

AI 输出可分为：有来源的事实、模型推断、用户自述、待确认信息。界面要让用户区分它们。

常见保护方式：结构化输出、原文引用、规则校验、工具结果回读、测试集、人工审核和“未命中/不知道”提示。

## AI 交互原则

1. 告诉用户系统依据什么资料得出结论。
2. 允许用户纠正资料或选择方向。
3. 高影响操作前要求确认。
4. 信息不足时解释缺什么，而不是补造。
5. 把内部实现复杂度隐藏在合理的交互之后，不要求用户手工维护 JSON 或提示词。

## AI 产品评测维度

- 任务完成度；
- 事实和引用正确性；
- 条件保真度；
- 工具选择和参数正确性；
- 延迟与成本；
- 用户能否理解、纠正和继续下一步；
- 失败是否可恢复。

# 交付、协作与迭代

## 原型层级

| 层级 | 目的 | 常见形式 |
| --- | --- | --- |
| 概念原型 | 验证用户是否理解价值 | 流程图、文案、可点击稿 |
| 行为原型 | 验证用户能否完成任务 | 手动服务、低代码工作流、模拟数据 |
| 技术原型 | 验证实现约束 | API 调用、数据管道、最小代码 |
| 可用版本 | 验证持续使用和运营 | 有状态、监控、异常处理的产品 |

不要把演示成功等同于可用版本；也不要在概念尚未验证时过早建设复杂基础设施。

## 与研发协作

产品经理需要让团队明确：问题、目标、用户流程、优先级、验收标准、数据与权限约束、未知风险。研发负责实现方案、技术拆解和工程质量；双方共同讨论取舍。

好协作不是把 PRD 扔给研发，而是在不确定项上尽早对齐：数据是否存在、延迟是否可接受、模型成本、失败模式、隐私和权限、上线监控。

## 发布前检查

- 核心流程是否可完成；
- 错误和空结果是否有解释；
- 用户输入是否被正确处理；
- 权限与敏感资料是否遵循最小必要原则；
- 指标、日志和反馈渠道是否准备；
- 是否有回滚或降级方案。

## 迭代节奏

每轮迭代只选择一个最重要问题：观察证据 → 定义假设 → 修改 → 测试 → 记录结果 → 决定扩大、修正或停止。持续积累失败案例，避免相同问题反复出现。
